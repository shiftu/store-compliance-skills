# 报告模板（Google Play）

一个 App 一份，五段固定顺序，`scripts/render_report.py <out_dir> <slug>` 生成。
段标题由脚本硬编码，`check_run.py` 逐段检查存在性；不要手写报告。

```
# <App 名> · Google Play 合规实测报告
- 应用 / 商店（店面）/ 开发者 / 抓取日 · 请求次数 · 证据文件数
- 判定口径：规则库文件名（生效 N 条；upcoming M 条单列第 4 段）
**风险等级：🔴/🟡/🟢/⚪**
（规则库 verified_on 超 60 天时，首段后插入「规则库可能过期」告示）

## 1. 结论
四项计数表 + 不符合按 severity 分布 + 一句话人话

## 2. 阻断项（下架级）
每条：rule_id 标题 / 结论 + 置信度 / 条号 + 来源 / 条款原句 / 证据（文件 + 逐字片段）/ 后果 / 判定说明 / 修法
（无则写「本店未发现下架级阻断项」+ 指向文末边界）

## 3. 疑似违规（拒审级 / 整改建议）
同上，按 removal > rejection > advisory 排序

## 4. 即将到期
| 规则 | 到期日 | 要做的事 | 依据 |
（无 upcoming 也要有这一段，写「本规则库当前无 upcoming 条款」）

## 5. 无法核实
| 规则 | 等级 | 为何判不了 | 谁能核实 |
+ 一行「前提不成立（不适用）」的 rule_id 清单

## 附：证据清单 / 方法与边界
`_raw/...` ← URL（kind）；取数、判定、证据口径、边界四行
```

## 写作规则

1. **不预测审核结果。** 不出现「会通过」「会被拒」「大概率过」「建议直接上架」。只写条款 + 证据 + 条款规定的后果。
2. **数字来自 `verdicts.json.summary`，不手算。** `check_run.py` 会重算并与 `summary` 比对。
3. **阻断项必须带修法。** `fix` 来自规则库；没写清改哪里等于没给结论。
4. **upcoming 只进第 4 段**，不进第 1 段计数，不参与风险等级。
5. **无法核实 ≠ 通过，也 ≠ 低风险。** 第 5 段必须写「拿到什么才能判」。
6. **抓取失败写进第 5 段**（`NOT_CHECKED`），不得混入「符合」。
7. **证据只允许 `find`（逐字存在）与 `absent`（机械确认缺失 + 说明为何算证据）**；评论、竞品、论坛只能当触发人工复核的信号。
8. **同一 App 重跑**：旧 `report.md` 被覆盖，`_raw/` 与 `_logs/` 追加，不删历史。
